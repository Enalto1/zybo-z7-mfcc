# MFCC 개발 인수인계

작성 기준: 2026년 10월 4일. 전체 자료 위치와 제출 일정은 [개발 저장소 안내](../README.md)를 따른다.

이 문서는 새 개발 대화가 동일한 요구에서 작업을 시작하도록 확정 사항과 미확정 사항을 구분한다. 구현이 완료되었다는 보고서가 아니다.

## 연구 배경과 목표

사용자는 예비캡스톤과 본 캡스톤을 통해 음성 특징 추출을 개발했으나, 당시 원하는 MFCC 하드웨어의 실제 보드 동작까지 완성하지 못했다. 이후 경기도팹리스아카데미 시스템반도체 설계 교육을 마쳤으며, 현재 ZYBO Z7-20에서 동작하는 MFCC 구현과 개인 학사논문을 준비하고 있다.

주요 목적은 AI 입력으로 사용할 음성 특징 추출기다. 이번 개발의 중심은 MFCC이며, 새로운 분류 신경망을 반드시 하드웨어로 구현하는 범위는 확정되지 않았다.

하드웨어의 필요성은 실험으로 평가한다. 단일 마이크의 MFCC는 ARM 소프트웨어로도 처리 가능할 수 있다. 후보 장점은 CPU 연산 부담 감소, 프레임 처리 시간과 처리량 개선, 고정소수점 설계의 자원 효율이다. 전력이나 인식 정확도의 우수성은 별도 측정 없이 결론 내리지 않는다.

## 확정된 개발 방향

| 항목 | 사용자 의도와 제약 |
|---|---|
| 대상 보드 | ZYBO Z7-20 |
| 출발점 | 아래 GitHub 프로젝트를 참고하고 필요한 부분을 이식 |
| 개발 흐름 | Python 모델 → C 모델 → 하드웨어 구현과 검증 |
| 계획한 비교군 | Python, ARM C, 부동소수점 IP 기반 HW, 고정소수점 custom RTL HW |
| 기존 FFT | 이전에 Codex와 개발한 구현을 재사용 후보로 점검 |
| 언어 | custom RTL은 Verilog를 목표로 검토. 기존 VHDL 모듈은 필요한 변경을 확인 |
| 협업 | Codex와 Claude Code가 하나의 프로젝트와 공통 규격을 사용 |
| Git | `project`만 저장소로 관리. 논문·발표 작업물은 제외 |

## 비교군의 역할

| 구현 | 역할 | 확인할 내용 |
|---|---|---|
| Python | 알고리즘 기준값과 시각화 | 중간 단계·최종 계수의 기준 데이터 |
| C 골든 모델과 ARM 실행 코드 | 소프트웨어 검증 및 동일 보드의 SW 성능 기준 | Python 대비 오차, ARM 실행 시간과 CPU 사용 방식 |
| 부동소수점 IP 기반 HW | 기존 설계의 재현·이식과 HW 성능 측정 | 실제 수치 표현, 출력 오차, 처리 시간, 자원 |
| 고정소수점 custom RTL HW | 비트 폭·연산 구조 설계의 효과 평가 | 비트 단위 일치, 허용 오차, 자원과 처리 시간 |

Python을 PC에서 실행한 시간은 알고리즘 개발 참고값으로 구분한다. ARM 대비 하드웨어 가속 효과의 직접 기준은 같은 보드에서 측정한 ARM C 구현이다.

C 모델의 연산 정의와 ARM 실행용 입출력·타이머 코드를 분리한다. ARM은 베어메탈을 우선 검토할 수 있으며, Linux 사용은 필수 요구가 아니다. 실행 환경의 최종 선택과 클록·컴파일 설정은 측정 기록에 남긴다.

고정소수점 RTL 검증에는 비트 폭, 반올림, 포화·오버플로, 스케일링을 모사한 Python 또는 C 모델을 추가하는 것을 권장한다. 이는 검증 보조 모델이며, 별도의 다섯 번째 성능 비교군을 의미하지 않는다.

이전에 개발한 FFT의 위치, 변환 길이, 비트 폭, 구조, 인터페이스, 검증 수준은 아직 모른다. 재사용을 결정하기 전에 소스와 테스트 결과를 확인한다.

## 아직 확정하지 않은 규격

다음 항목은 기존 보고서나 라이브러리 기본값에서 임의로 가져오지 않는다. 원본 설계와 기존 FFT를 점검한 뒤 공통 규격 문서 한 곳에서 확정한다.

- 입력 PCM의 샘플링 주파수, 채널 수, 비트 폭과 진폭 정규화.
- 프리엠퍼시스 사용 여부와 계수, 프레임 길이와 이동 간격.
- 프레임 경계·패딩·마지막 프레임 처리, 윈도 함수와 계수.
- FFT 길이, 부호, 출력 bin 순서, 내부·출력 스케일링.
- 크기 또는 파워 스펙트럼의 정의와 정규화.
- Mel 변환식, 주파수 범위, 필터 수, 필터 가중치와 정규화.
- 로그 밑과 하한값, DCT 유형·정규화, MFCC 계수 수.
- C0·프레임 에너지 대체, lifter, delta·delta-delta의 포함 여부.
- 고정소수점 단계별 비트 폭과 소수부, 반올림·포화 정책.
- 프레임 및 계수 출력 순서, 허용 오차, 목표 처리량과 자원 예산.
- ARM과 HW 간 데이터 경로, DMA·인터럽트·폴링 방식과 측정 범위.

기존 보고서에는 서로 다른 설정의 실험이 포함되어 있으므로 하나의 일관된 규격으로 간주하지 않는다. 이번 비교에 사용할 수치와 연산 정의를 별도로 검증한다.

## 검증과 성능 비교 원칙

1. 공통 PCM과 동일한 프레임 경계를 사용한다. 입력 파일과 계수 테이블을 식별할 수 있게 기록한다.
2. 중간 단계와 최종 MFCC 계수를 비교한다. FFT 단독 통과와 MFCC 전체 통과를 구분한다.
3. 계수별 오차와 최대 절대 오차·RMSE 등을 기록한다. 0에 가까운 기준값에 대한 상대 오차 해석에 주의한다.
4. MFCC는 시간과 계수 번호를 축으로 하는 히트맵으로 비교한다. 주파수축 스펙트로그램과 구분하며, 같은 프레임·축·색 범위를 사용한다.
5. 처리 시간은 연산 구간과 데이터 전송·캐시 처리·제어를 포함한 전체 구간을 구분한다. 한 프레임의 지연과 연속 프레임 처리량을 별도로 기록하고, UART 출력 시간은 연산 시간과 분리한다.
6. ARM 기준은 적절한 최적화와 동일한 연산 정의를 사용한다. 클록, 컴파일 옵션, 캐시 상태, 반복 횟수와 통계 방법을 기록한다.
7. HW 결과 대기 중 CPU가 계속 폴링했다면 CPU가 해방되었다고 단정하지 않는다. 처리 시간 감소와 CPU 사용 시간 감소를 구분한다.
8. FPGA 자원과 동작 주파수는 같은 대상 소자와 도구·제약 조건을 기준으로 비교한다. 합성 추정과 구현 후 결과, 실제 보드 측정을 구분한다.
9. 고정소수점의 수치 오차가 작다는 사실만으로 AI 인식률이 유지된다고 단정하지 않는다. 전력 측정이 없으면 저전력은 향후 평가 항목으로 남긴다.

## 구현 우선순위 제안

먼저 저장된 공통 입력으로 기준 모델과 기존 HW의 한 경로를 끝까지 검증하고, 보드에서 계수를 회수하는 경로를 확보하는 것을 권장한다. 실시간 마이크·코덱 연결과 추가 기능의 우선순위는 일정에 맞춰 결정한다.

네 비교군을 모두 완성하는 것은 목표이며 완료 사실이 아니다. 초기 코드 점검 뒤 제출 전에 확보할 필수 결과와 추가 구현 범위를 나눈다. 기존 FFT는 검증에 통과한 경우 재사용하며, 모든 FFT를 새로 작성하는 것을 선행 조건으로 만들지 않는다.
