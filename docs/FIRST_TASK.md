# 첫 개발 작업

목표는 기존 GitHub MFCC와 이전 FFT의 재사용 가능성을 확인하고, Python·C·HW가 공유할 연산 규격을 정하는 것이다. 전체 구현을 시작하기 전에 무엇을 재사용하고 무엇을 수정할지 근거를 확보한다.

먼저 [개발 저장소 안내](../README.md)와 [개발 인수인계](DEVELOPMENT_HANDOFF.md)를 읽는다. 작업 폴더는 `D:\2610_MFCC\project`이며, 참고 원본은 상위의 `reference_code`와 `references`에서 읽는다.

## 시작 시 확인할 사항

- 현재 폴더와 기존 파일, Git 상태, 적용되는 작업 지침을 확인한다. 사용자의 미반영 변경을 덮어쓰지 않는다.
- 기존 FFT와 사용 중인 Vivado 프로젝트의 정확한 위치를 확인한다. 위치가 제공되지 않았다면 해당 경로만 사용자에게 요청하고, GitHub 원본 점검 등 독립 작업을 계속한다.
- 설치된 Vivado·Vitis 또는 SDK·시뮬레이터·C 컴파일러·Python 환경의 버전을 확인한다. 새 도구 설치를 점검의 선행 조건으로 만들지 않는다.
- 참고 GitHub와 현재 프로젝트의 기준 버전, 라이선스, 대상 FPGA, 필요한 IP를 기록한다. 네트워크나 파일 접근이 불가능하면 확인하지 못한 항목을 명시한다.

## GitHub MFCC 점검

1. 최상위 모듈에서 음성 입력, MFCC, 분류기, 디버그 회로의 경계를 확인한다. MFCC만 실행하는 데 필요한 모듈과 IP 목록을 만든다.
2. MFCC 출력에 프레임 에너지 대체, lifter, delta 등이 포함되는지 확인한다. 이번 비교의 출력 위치를 명확히 한다.
3. 샘플링·프레임·FFT·Mel·로그·DCT 설정을 코드와 계수 테이블에서 추출한다. 문서와 코드가 다르면 차이를 기록한다.
4. Xilinx IP 설정 파일과 생성 방법, 메모리 초기화 파일, 클록과 리셋, 데이터 유효 신호와 프레임 경계를 점검한다.
5. Kintex 대상 설정에서 ZYBO Z7-20으로 옮길 때 필요한 변경을 구분한다. 소자, 보드 제약, 클록, 메모리, PS와 PL 사이 데이터 경로를 확인한다.
6. 기존 VHDL의 문제는 증거를 확인한 뒤 수정 후보로 기록한다. 언어 변환 자체를 목표로 삼지 않는다.

## 기존 FFT 점검

다음 항목을 실제 소스 및 테스트와 대조한다.

| 항목 | 확인할 내용 |
|---|---|
| 연산 | FFT 길이, 순방향 부호, 실수·복소수 입력 지원 |
| 출력 순서 | 자연 순서 또는 bit/digit reversal 여부, bin 식별 |
| 수치 표현 | signed 여부, 입력·내부·출력 비트 폭, 소수부 위치 |
| 스케일링 | 단계별 시프트, 전체 배율, 반올림·포화·오버플로 |
| 인터페이스 | 입력 수락 조건, valid/ready 등 흐름 제어, 프레임 경계 |
| 클록과 리셋 | 클록 도메인, 리셋 극성과 동기 여부, 리셋 후 첫 프레임 처리 |
| 시간 동작 | 지연, 다음 프레임 수락 간격, 멈춤 상황의 동작 |
| 검증 근거 | 테스트벤치, 기준값, 시뮬레이션·합성·구현·보드 검증 여부 |

기존 테스트를 먼저 확인하고, 부족한 핵심 항목에 대해서만 임펄스·DC·정수 bin 정현파·무작위 입력 등 필요한 시험을 보완한다. 해당 FFT의 출력 순서와 배율을 반영한 기준값으로 비교한다.

검토 결과는 그대로 재사용, 연결·배율 보정 후 재사용, 내부 수정 필요, 이번 일정에서 사용 보류 중 하나로 정리하고 근거를 적는다. 기존 FFT의 구조를 확인하기 전에는 고정소수점 구현이라고 가정하지 않는다.

## 공통 규격 초안과 범위 확정

점검에서 확인한 설정으로 `docs/MFCC_SPEC.md` 초안을 작성한다. 각 항목에 확정·제안·미확인 상태와 근거를 붙인다. [개발 인수인계](DEVELOPMENT_HANDOFF.md)의 미확정 규격 목록을 빠짐없이 검토한다.

원본과 기존 FFT를 함께 사용할 수 있는 가장 작은 구현 범위를 제안한다. 비교 결과를 바꾸는 선택이나 사용자 의도가 필요한 항목은 핵심 질문으로 모으고, 단순 연결과 파일 배치 같은 구현 선택은 근거를 기록하며 진행한다.

공통 검증 입력과 작은 테스트벡터, 기준 계수 생성 방식도 정한다. 공통 규격이 확정되기 전에 서로 다른 설정의 구현을 성능 비교 결과로 합치지 않는다.
